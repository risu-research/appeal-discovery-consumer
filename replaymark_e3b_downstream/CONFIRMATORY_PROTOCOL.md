# ReplayMark E3b downstream benchmark-conclusion experiment — confirmatory freeze

Status: **FROZEN BEFORE CONFIRMATORY IMPLEMENTATION / EXECUTION**.

This protocol is the authority for the downstream E3b confirmatory experiment. The broad queue sweep in run `34001663313` was explicitly exploratory and is not admissible as the paper's confirmatory result.

## 1. Scientific question

Does a timing-reactive replay that is invalid at the target-controller boundary lead to a wrong engineering conclusion about a real Mosquitto target?

The downstream decision is deliberately concrete and threshold-free:

> **What is the minimum Mosquitto `max_queued_messages` setting that preserves all QoS 1 messages generated by one 128-task target batch for an offline persistent consumer?**

A benchmark based on R1 and a benchmark based on direct target-native execution will answer this same provisioning question.

## 2. Why this is downstream rather than another workload-count result

The frozen E3b result already established 512 broker-native PUBLISH operations for R1 and 768 for semantic replay. This experiment does not count those operations again as its endpoint. It places the corresponding target workload behind a real Mosquitto 2.1.2 persistent-session queue and measures the broker's externally visible delivery consequence after the consumer reconnects.

The primary outcome is therefore a real configuration decision and real message loss/survival, not an inferred loss model.

## 3. Platform and immutable semantic parameters

- Broker image tag: `eclipse-mosquitto:2.1.2-alpine`.
- The resolved image digest must be recorded in every raw artifact; confirmatory validation fails if replicas resolve different digests.
- MQTT QoS: 1 for all measured command/query/state messages.
- Tasks: 128.
- Wave size: 32.
- Wave period: 300 ms.
- Controller decision deadline: 100 ms.
- Target state delay: 150 ms.
- Post-completion gap: 20 ms.
- Per-task timeout: 1200 ms.
- `max_queued_bytes = 0` so the experiment isolates the message-count queue bound.
- `max_inflight_messages = 20` and `queue_qos0_messages = false` are fixed across all cells.

The persistent consumer subscribes to the exact per-run command/query/state namespace, establishes the session, then disconnects before the measured batch. After the batch is independently observed to have generated its exact expected message count, the same persistent client reconnects and drains to a quiescent barrier.

## 4. Conditions

### R1_TIMING

Timing follows actual target completion while the source semantic sequence remains `ACT1 -> ACT2`. Under the frozen target condition the controller-required VERIFY branch is omitted. This condition is expected to remain support-invalid in all tasks.

### TARGET_NATIVE

A direct implementation of the frozen target controller executes against target feedback. Missing feedback at the 100 ms decision deadline causes VERIFY, then ACT2 after verification. This implementation is code-path independent of the R2 table interpreter.

### R2_SEMANTIC

The same frozen controller semantics are executed through the explicit semantic replay/table interpreter. R2 is a cross-check, not the definition of native ground truth. It must agree with TARGET_NATIVE on semantic multiplicity and the downstream provisioning conclusion.

## 5. Confirmatory queue points — fixed mechanically before execution

The frozen E3b semantic counts predict exact queue requirements of 512 messages for R1 and 768 for target-native/R2. The exploratory pilot showed no hidden Mosquitto queue-accounting offset. The confirmatory experiment therefore tests the one-message neighborhoods of the two independently predicted boundaries:

`511, 512, 767, 768`

No other queue value may be substituted after confirmatory outcomes are observed.

## 6. Replication and order

- Two independent GitHub-hosted Ubuntu runner jobs per queue point: replicas `A` and `B`.
- Six trials per `(replica, queue_limit)`.
- Each trial executes all three conditions once.
- Mode order is counterbalanced by a fixed six-permutation cycle; the cycle is identical across queue points and replicas.
- Every `(replica, queue_limit)` starts a fresh Mosquitto process and empty in-memory session store.
- Each trial/condition uses a unique MQTT namespace and persistent-session client identifier.

This yields `2 replicas x 4 queue points x 6 trials x 3 conditions = 144` measured condition executions. Task-level events are not treated as independent statistical replicates.

## 7. Exact primary and boundary predictions

Let `G_m` be generated measured QoS 1 messages and `D(q,m)` be messages delivered to the persistent consumer after reconnect. `L(q,m) = G_m - D(q,m)`.

Implementation/semantic conservation predictions:

- `G_R1 = 512` in every trial.
- `G_NATIVE = G_R2 = 768` in every trial.
- R1 support-violation fraction = `1.0`.
- TARGET_NATIVE and R2 support-violation fraction = `0.0`.
- TARGET_NATIVE and R2 execute VERIFY in `128/128` tasks.

Downstream predictions:

| q | R1 loss | TARGET_NATIVE loss | R2 loss |
|---:|---:|---:|---:|
| 511 | 1 | 257 | 257 |
| 512 | 0 | 256 | 256 |
| 767 | 0 | 1 | 1 |
| 768 | 0 | 0 | 0 |

### Primary benchmark-conclusion test

At `max_queued_messages = 512`:

- R1 must classify the broker configuration as **LOSSLESS**.
- TARGET_NATIVE must classify the same broker configuration as **LOSSY**, losing exactly `256/768 = 1/3` of the generated target-workload messages.
- R2 must agree with TARGET_NATIVE.

This is the primary downstream conclusion disagreement.

### Exact provisioning-boundary test

- R1: q=511 loses exactly one message and q=512 is lossless, establishing a 512-message lossless boundary.
- TARGET_NATIVE/R2: q=767 loses exactly one message and q=768 is lossless, establishing a 768-message lossless boundary.

Thus the target-native requirement is predicted to be exactly `768/512 = 1.5x` the requirement inferred from R1. Equivalently, provisioning from R1 underallocates the target-native requirement by `256/768 = 33.3%`.

## 8. Evidence and failure gates

A raw condition is admissible only if:

1. all 128 workload tasks complete;
2. the online observer independently sees the exact generated-message count before offline drain;
3. the persistent session is present on reconnect;
4. collector duplicate count is zero;
5. R1/native/R2 semantic support checks match the frozen controller semantics;
6. the measured queue configuration is the declared matrix value; and
7. the broker image digest is recorded.

Any failed implementation gate invalidates that raw cell. A failed scientific prediction is retained as a genuine falsification and may not be converted into an implementation failure unless the above gate itself fails.

## 9. Independent validation

The experiment runner writes raw JSON only. A separate validator, executed after all matrix jobs, must consume the artifacts without importing the experiment runner and produce a confirmation certificate. The validator checks:

- complete replica/queue/trial coverage;
- common broker digest;
- semantic/generated-message conservation;
- exact loss table above;
- native/R2 agreement;
- primary q=512 conclusion disagreement; and
- exact 512-versus-768 provisioning boundary.

The confirmatory certificate, not an exploratory artifact, is the authority for any manuscript claim.

## 10. Reporting rule

The confirmatory result will be reported exactly as observed across both canonical replicas and all six trials. Because the decisive outcomes are structural integer conservation/loss properties of a frozen deterministic protocol, no task-level p-value or pseudo-replication is permitted. Timing may be reported descriptively but cannot replace or redefine the primary endpoint.
