## Downstream question fixed before pilot

**Can a timing-reactive but semantically invalid replay lead to the wrong broker-provisioning conclusion for the same target workload?**

The engineering decision is the minimum Mosquitto offline-session queue capacity required to preserve all QoS 1 messages generated by one 128-task target batch.

This is downstream of the already-established semantic distinction: the outcome is not merely action count. It is whether a real Mosquitto configuration preserves or loses target-workload messages.

## Real system mechanism

A persistent MQTT subscriber first installs QoS 1 subscriptions for the experiment's command, query, and state topics, then disconnects while retaining its session. The E3b workload executes while the subscriber is offline. Mosquitto therefore queues matching QoS 1 messages subject to its real `max_queued_messages` configuration. The subscriber reconnects after the workload and counts delivered messages.

No synthetic dropper or post-hoc loss model is admitted. Loss/survival must be produced by Mosquitto 2.1.2 itself.

## Conditions

- `R1_TIMING`: target timing is followed while the frozen source semantic sequence is retained.
- `TARGET_NATIVE`: an independently coded direct execution of the frozen target controller rule. At the decision deadline, missing target feedback causes VERIFY; after verification, ACT2 follows. This condition is not implemented by calling the R2 function.
- `R2_SEMANTIC`: retained as a cross-check. It must agree with TARGET_NATIVE on projected action path and downstream conclusion before R2 may be used as a semantic replay reference.

## Fixed downstream endpoint

For each queue limit `q` and condition `m`:

- `generated_qos1(m)`: exact matching QoS 1 messages generated during the measured batch.
- `delivered_qos1(q,m)`: messages recovered by the persistent subscriber on reconnect.
- `loss(q,m) = generated_qos1(m) - delivered_qos1(q,m)`.
- A configuration is **LOSSLESS** iff `loss(q,m) = 0` and all workload tasks complete successfully.

The downstream benchmark conclusion is the **minimum tested `max_queued_messages` that is LOSSLESS**. No latency/SLA threshold is selected from observed results.

## Pilot queue sweep

The exploratory implementation pilot tests the predeclared queue limits:

`256, 384, 512, 640, 768, 896, 1024` messages.

The pilot has exactly two purposes:

1. validate persistent-session accounting against broker-native generated-message conservation; and
2. determine whether Mosquitto's documented queue semantics introduce an offset (for example, in-flight accounting) that must be represented explicitly in the confirmatory protocol.

The confirmatory sweep will be frozen in a new protocol commit only after this implementation/range validation. Any queue limits used in the confirmatory experiment must be chosen by a mechanical rule stated in that freeze; they cannot be selected to maximize a result.

## Pilot acceptance checks

The pilot implementation is scientifically usable only if all checks hold:

1. clean broker instance per `(queue_limit, condition)`;
2. persistent session is established and subscription acknowledgements are observed before disconnect;
3. only experiment command/query/state topics are counted;
4. generated matching QoS 1 count is independently conserved from runner/device evidence;
5. R1 remains support-invalid under the frozen target condition;
6. TARGET_NATIVE and R2 are support-valid and generate the same semantic path multiplicity;
7. reconnect drain reaches a quiescent barrier rather than using a guessed sleep;
8. no queue limit, message count, or loss rule is changed after seeing pilot outcomes without recording the change as an implementation finding.

## Interpretation discipline

The desired high-value pattern is that an R1-based benchmark selects a smaller queue configuration as lossless while TARGET_NATIVE demonstrates loss under that same real broker configuration. The pilot is allowed to falsify this pattern. A null result or an unexpected Mosquitto queue-accounting rule will be preserved and used to redesign or abandon the downstream mechanism; it will not be hidden or threshold-tuned.
