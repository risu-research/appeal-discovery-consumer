## Design actually executed

The engineering question was fixed as:

> What is the minimum real Mosquitto `max_queued_messages` setting that preserves all QoS 1 messages generated by one 128-task target batch for an offline persistent consumer?

Four queue points were mechanically fixed from the independently established E3b semantic counts and the pilot's no-offset finding: `511, 512, 767, 768`.

Two independent GitHub-hosted replicas (`A`, `B`) each ran six trials at every queue point. Every trial executed R1 timing-reactive replay, a direct target-native controller implementation, and the independent R2 semantic-replay interpreter in a fixed counterbalanced six-permutation order. This produced 144 measured condition executions and 18,432 task executions. Task-level events were not treated as independent statistical replicates.

The target-native condition did not call the R2 interpreter. It directly implemented the frozen target controller rule: missing feedback at the 100 ms decision deadline causes VERIFY, followed by ACT2. R2 was retained only as a separate semantic-replay cross-check.

## Exact result

Every one of the 144 measured condition executions passed its implementation and semantic gates. Across both replicas and all six trials per queue point, the observed generated/delivered/lost counts were exact and identical to the frozen predictions:

| `max_queued_messages` | R1 timing replay | Target-native | R2 semantic replay |
|---:|---:|---:|---:|
| 511 | 512 / 511 / **1 lost** | 768 / 511 / **257 lost** | 768 / 511 / **257 lost** |
| 512 | 512 / 512 / **0 lost** | 768 / 512 / **256 lost** | 768 / 512 / **256 lost** |
| 767 | 512 / 512 / **0 lost** | 768 / 767 / **1 lost** | 768 / 767 / **1 lost** |
| 768 | 512 / 512 / **0 lost** | 768 / 768 / **0 lost** | 768 / 768 / **0 lost** |

Each table entry above held in all `2 replicas x 6 trials = 12` corresponding cells. In the aggregate certificate, for example, q=512 produced 6,144/6,144 delivered messages under R1 but only 6,144/9,216 under both target-native and R2, i.e. exactly 3,072 native-workload messages lost across the 12 cells.

The semantic boundary was also reproduced in every condition: R1 support-violation fraction was `1.0`; target-native and R2 support-violation fraction was `0.0`; target-native and R2 each executed VERIFY in `128/128` tasks per condition. Persistent sessions were present on reconnect and collector duplicate count was zero.

The independent validator consumed the eight raw JSON artifacts without importing the experiment runner and returned `confirmation_pass = true` with an empty error list. All primary and boundary checks passed.

## Downstream benchmark conclusion

The same real Mosquitto configuration receives opposite engineering classifications depending on replay semantics:

- At `max_queued_messages = 512`, R1 classifies the configuration as **LOSSLESS** in all 12 confirmatory cells.
- The direct target-native execution classifies that exact same configuration as **LOSSY** in all 12 cells, dropping exactly `256/768 = 1/3` of the target-native QoS 1 workload.
- R2 independently agrees with target-native in all 12 cells.

The exact lossless provisioning boundary is therefore:

- **R1 timing-reactive replay: 512 messages.** q=511 loses exactly one message per trial; q=512 is lossless.
- **Target-native controller: 768 messages.** q=767 loses exactly one message per trial; q=768 is lossless.
- **R2 semantic replay: 768 messages.** It exactly reproduces the target-native boundary.

Thus timing-reactive replay underestimates the real target-native lossless queue requirement by 256 messages, or **33.3% of the target-native requirement**. Equivalently, the target-native requirement is exactly **1.5x** the queue size inferred from R1.

## Scientific interpretation

This experiment closes the downstream link that the original E3b workload-count result did not by itself establish. The consequence is no longer only that semantic replay generates 1.5x more native work. In a real Mosquitto 2.1.2 broker mechanism, the semantically invalid timing-reactive replay leads the benchmark to select a concrete queue configuration that appears lossless under replay but loses one-third of the workload generated by the target controller under the same target conditions.

The result is deliberately bounded. It establishes a real, reproducible existence result for this frozen E3b provisioning benchmark; it does not estimate how frequently trace replay causes wrong provisioning decisions across deployed MQTT systems. The manuscript claim should preserve that scope.
