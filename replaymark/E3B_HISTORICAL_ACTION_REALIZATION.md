# ReplayMark E3b historical-action realization

## Status

This increment extends the frozen runtime-realization boundary at
`replaymark-runtime-realization-observation@a711bc54a95b236beed32c270d58078e241cacaf`
with **exactly one new concrete realizer**:

```text
resolved E3b candidate MQTT publish
        -> RealizedHistoricalAction
```

It does not call `CompiledContract`, construct a live `RuntimeReuseCertificate`,
execute or block an MQTT publish, select fallback/regeneration, modify R0/R1/R2,
or change any semantic compiler theorem.

The earlier `RUNTIME_REALIZATION_BOUNDARY.md` is retained as the historical
freeze document for the observation-only increment. This document is the
additive authority for the action side.

## 1. The object being realized

A subtle but important E3b fact is that the experiment does **not** replay the
literal source MQTT packet bytes.

The frozen source trace retains the controller decision sequence and timing. In
the target run, `target_task` creates a fresh task-local stage-2 device and
issues a new publish for the retained `ACT2` decision.

Therefore the runtime obligation is not:

```text
source packet bytes == target packet bytes
```

It is:

```text
actual target-run candidate publish
        realizes
frozen historical controller decision ACT2
```

This distinction keeps ReplayMark's claim at the decision-semantics boundary
already used by the E3b target model.

## 2. Capture boundary

The raw source schema describes the resolved arguments of the existing
application call immediately before send:

```text
paho.mqtt.Client.publish.pre-send
```

Required fields are:

```text
schema
capture_point
clock_domain
publish_mono_ns
topic
payload_utf8
qos
retain
properties
```

This boundary certifies the intended concrete publish invocation. It does **not**
certify broker delivery, PUBACK, downstream processing, or endpoint state
transition. Those are execution/runtime effects and remain outside this
increment.

## 3. No caller-supplied semantic labels

The raw record deliberately has no fields named:

```text
operation
target_class
variant
delay_ms
```

A caller cannot say "this is ACT2" and obtain a certificate.

The realizer derives the modeled coordinates only after the concrete publish
matches the frozen E3b producer contract.

Any extra caller field, including an `operation=ACT2` field, is rejected as a
malformed source record.

## 4. Frozen concrete ACT2 producer contract

The admitted action is intentionally narrow:

```text
topic      = agentmark/<prefix>-<task-id>-b/command
payload    = {"on": true}        # exact UTF-8 producer encoding
qos        = 1
retain     = false
properties = null
```

`task-id` must be canonical ASCII decimal (`0`, `1`, ..., but not `00` or
`01`). `prefix` is opaque to the realizer: it does not inspect R0/R1/R2 policy
names. This prevents execution-policy metadata from leaking into action
semantics.

The final `b` role is what the frozen E3b harness uses for the stage-2 device.
Stage-1 `a` commands, queries, other topic families, and other task-role
encodings are not ACT2 realizations.

## 5. Conservative payload semantics

The legacy E3b device happens to execute:

```python
states[device] = bool(body.get("on", True))
```

Therefore many alternate payloads could happen to turn the device on, including
payloads such as `{}`, `{"on": 1}`, or truthy strings.

ReplayMark deliberately does **not** widen the realization relation to those
coercions.

Only the exact producer output from the frozen harness is admitted:

```text
{"on": true}
```

Even semantically equivalent alternate whitespace such as `{"on":true}` is
rejected. This is conservative by construction: this increment certifies the
historical action actually generated by the frozen producer, not an inferred
class of device-equivalent MQTT messages.

Duplicate JSON keys and malformed JSON are rejected as malformed input.

## 6. Derived semantic coordinates

After the concrete publish is admitted, the realizer derives the exact legacy
TargetModel coordinates:

```text
operation    = ACT2
target_class = stage2
variant      = null
delay_ms     = 0
```

It also preserves claim-independent concrete coordinates:

```text
concrete_target
 task_id
 task_prefix
 mqtt_topic
 mqtt_qos
 mqtt_retain
 mqtt_payload_sha256
```

The concrete coordinates are audit/provenance information. A `ClaimSpec`
continues to decide which action coordinates are consequential.

The verifier explicitly checks that projection onto the four legacy model
coordinates equals the action emitted by the already-frozen E3b
`TargetModel` for `after_act1 / confirmed_by_deadline`.

## 7. Source-code provenance hardening

The realizer rule is content-addressed and is additionally bound to the exact
Git blob identities of the frozen producer and consumer:

```text
agentmark_e3b_lab/e3_mqtt/app/ladder.py
  fcc1768544714f1b11a497a856f8e18d4d2f07dd

agentmark_e3b_lab/e3_mqtt/app/device.py
  27240e65cb8e1a7d788cc5dea8484cbad8ec6653
```

CI recomputes the Git blob hash from the checked-out bytes. A later edit to the
legacy E3b producer or device therefore cannot silently inherit this realization
certificate.

This is intentionally stronger than a human-readable adapter version string.

## 8. Provenance separation

Every successful result carries `RealizationProvenance` with:

```text
stage = HISTORICAL_ACTION
realizer_id
realizer_semantic_digest
source_schema
raw_record_digest
```

Changing the raw publish timestamp changes the raw-record digest but does not
change the derived action coordinates or the realizer semantic digest.

Changing the realization rule must change the semantic digest.

Timing is retained in the raw provenance record rather than inserted as an
action coordinate, because issue time is not part of the frozen E3b ACT2
controller-event identity.

## 9. Fail-closed classes

Examples:

```text
missing required field       -> MISSING_REQUIRED_FIELD
wrong Python/source type      -> MALFORMED_INPUT
malformed or duplicate JSON   -> MALFORMED_INPUT
stage-1/query/foreign topic   -> UNKNOWN_SEMANTIC_VALUE
noncanonical task id          -> UNKNOWN_SEMANTIC_VALUE
payload not exact frozen ACT2 -> UNKNOWN_SEMANTIC_VALUE
qos/retain/properties change  -> UNKNOWN_SEMANTIC_VALUE
```

These are runtime realization failures, not semantic `INVALID` or
`UNRESOLVED` verdicts.

A correct future bridge must not call `CompiledContract` after realization
failure.

## 10. Independent oracle

`replaymark_oracle/e3b_action_oracle.py` imports neither the production action
realizer nor the generic runtime-realization module.

The production parser identifies the task role with right-splitting. The oracle
uses an independently written anchored regular expression and reconstructs the
expected action from plain mappings.

The differential gate compares:

```text
success/failure
failure class
derived full action coordinates
```

across a systematic cross-product of topic, payload, QoS, retain, and property
variants, plus explicit malformed-shape cases.

## 11. Explicit non-goals

This increment does not establish:

- generic MQTT action equivalence;
- arbitrary Paho publish realization;
- wire-packet identity;
- broker delivery or QoS completion;
- physical endpoint realization;
- Home Assistant action realization;
- observation/action bridge construction;
- `RuntimeReuseCertificate` live construction;
- execution blocking;
- regeneration/fallback policy;
- runtime latency numbers.

## 12. Next admissible boundary

Once this gate is frozen, both theorem inputs have independent concrete
realizers for E3b:

```text
raw observation -> RealizedObservation
raw ACT2 publish -> RealizedHistoricalAction
```

The next atomic step may then join those two already-certified values to the
existing `ExplicitCompiledContract` in **shadow mode**, constructing a
`RuntimeReuseCertificate` without changing execution.

That bridge must reuse the existing `adjudicate` / `certify_reuse` methods; it
must not duplicate support or R* logic.
